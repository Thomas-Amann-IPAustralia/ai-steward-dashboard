# Independent review — AI Steward Dashboard

**Date:** 16 September 2026
**Scope:** whole repository, backend and frontend, plus the live data the pipeline
has produced since 2 August 2026.
**Method:** code read end to end; `runs.jsonl` (675 records), `history.json` (192
archived analyses), `health.json` and `hashes.json` analysed; the two failing
sources fetched independently to confirm root cause; the test suite run (57 tests,
all pass).

This review is deliberately independent of `CLAUDE.md`, `BUG_REPORT.md` and
`UPGRADE_PLAN.md` — those describe what was intended. This describes what is
actually running.

---

## 1. Verdict

**The engineering is genuinely good. The operations are not, and the gap is now
visible on the live site.**

The gate architecture — probe → validate → normalise → hash → diff → cosmetic →
fingerprint → LLM — is the right design, cleanly factored, and unusually well
tested for a project this size. Letting the model return `no_material_change` and
stamping the timestamp in code are the two best trust decisions in the codebase.
The August upgrade did what it set out to do: it stopped the pipeline
manufacturing changes that never happened.

But the tool's purpose is not "don't cry wolf". It is **"tell a public servant when
something they rely on changes."** Measured against that, three things are wrong
right now:

| | |
|---|---|
| **2 of 8 monitored sources have never been read successfully** | 5 documents, 35 consecutive failed runs, over a month |
| **30% of every document check since 13 August was a failure** | 203 `suspect_scrape` out of 675 records |
| **4 of 8 live analyses on the site carry hallucinated 2024 dates** | including a `critical` badge dated *16 May 2024* |

None of these is a bug in the new code. All three are the same underlying
problem: **the system detects and reports its own failures perfectly well, and then
nothing happens.** There is no loop that closes. A source fails, an issue is
commented on, the run moves on, and 35 days later the state is identical.

The priority signal is also inflating badly (§3.4): 48 of 192 archived analyses are
`critical` — 83% of May 2026, 65% of June. Three of eight sets wear a critical
badge today. If a quarter of everything is critical, nothing is.

**The two features you asked about are both worth building, and I'd sequence them
RSS-news → source editor → email newsletters (§5, §6, §8).** But I would spend half
a day on §3.1 first, because a dashboard showing a critical change dated May 2024
undermines every other thing on it.

## 2. What is working, and should not be touched

Short, because the point of a review is the other list — but these are real and
worth protecting.

- **`steward/` is properly pure.** Every module is importable and testable without
  network, browser or API key, and the test suite proves it. This is why the
  upgrade was possible at all, and why the GUI in §5 is cheap.
- **Real incidents used as test fixtures.** `tests/test_pipeline.py` pins the 7–8
  August Perplexity false positive using the archived captures. That is regression
  testing done properly.
- **Idempotent normalisation, pinned by test.** The single most load-bearing
  invariant in the pipeline, and it is guarded.
- **Per-document hashing with a set-level rollup.** Fixes the "one URL fails so the
  whole set looks changed" class of error at the root.
- **The model is allowed to decline.** 5 of 10 analyses since 13 August returned
  `no_material_change` and correctly did not badge the set.
- **The diff, not the documents, goes to the model.** Roughly 2,800 prompt tokens per
  analysis on average. Cheap, and sharper.
- **The frontend leads with the diff, dates its badges, and surfaces health.**
  `DiffView`, `PriorityBadge` and `SourceHealth` are all doing exactly the job
  their docstrings claim.
- **Lettermarks instead of `google.com/s2/favicons`.** The right call for an
  APS-facing tool, and the reasoning is documented in the component.
- **The documentation.** `BACKEND.md` and `CLAUDE.md` are better than most
  commercial codebases manage.

## 3. Findings

Ordered by how much they cost you. Each has evidence, a root cause, and a fix.
Effort: **S** ≈ under an hour, **M** ≈ half a day, **L** ≈ multiple days.

### 3.1 — The live dashboard is displaying pre-upgrade hallucinated analyses (Critical, S)

Four of the eight files in `analysis/` — the ones the detail page renders as
*the current analysis* — were written by the old pipeline and never replaced,
because those sources have not materially changed since:

```
2024-05-10  high      ACSC Information Security Manual (ISM)
2024-05-16  critical  Perplexity AI Legal Policies
2024-07-30  low       Google AI Policies
2024-07-30  medium    NSW Government AI Guidance
```

Those dates are model inventions — the exact bug `steward/analysis.py` was
rewritten to prevent. The consequence on the live site:

- **Perplexity's detail page reads "CRITICAL · 16 May 2024"** while the sidebar for
  the same set reads "last amended 9 Aug 2026". Two contradictory dates, one page.
- That critical is the 8–9 August false positive itself — *"replacing a previously
  inaccessible page"* is the Chrome error page, not a policy change. The upgrade
  stopped the mechanism producing new ones; nobody retracted the one already on
  the board.
- These four files have no `verdict` and no `diff_stats`, so the UI silently
  renders them with none of the new context.

**Fix.** A one-off repair script, plus a guard so it can't recur:

1. `scripts/repair_legacy_analyses.py` — for any `analysis/*.json` with no
   `verdict` key, set `date_time` from `hashes.json[setName].last_amended` (the
   pipeline's own record, not the model's), and add `"legacy": true`.
2. `PolicyDetail.js` — when `legacy` is set, render a banner: *"This analysis was
   produced before the current pipeline. Its date and priority have not been
   verified; the change history below is authoritative."*
3. For Perplexity specifically, the honest action is to retract: replace it with a
   `no_material_change` stub noting the 8 August capture failure, and keep the
   original in `logs/` where it already is.

This is under an hour of work and it is the difference between a dashboard people
trust and one they learn to discount.

### 3.2 — Two sources have never been read, for 35 runs, with a diagnosed cause (Critical, M)

**`Digital.gov.au AI Policy` — 4 documents, 0 successful reads ever.**

The site sits behind a WAF (Imperva-flavoured) that serves a short interstitial to
datacenter IPs with an HTTP 200. The pipeline escalates to Selenium — GitHub
Actions' IP is blocked there too — and captures 256 characters of *"Here are some
possible reasons why your information cannot be processed"*. Validation rejects it
as `too_short`. Every day. Fetching this URL from an independent host today
returns the same interstitial at 522 characters.

Two problems, and the second is the important one:

1. **That interstitial is not in `validation.failure_signatures`.** So
   `_looks_like_block_page` (`steward/fetching.py:306`) returns `False` and the
   fetcher believes it succeeded. Only `min_length` catches it — and the copy I
   pulled today was **522 characters, comfortably over the 500 floor**. Length is
   doing a job that a signature should be doing. Add these:

   ```yaml
   - "your information cannot be processed"
   - "Request unsuccessful. Incapsula incident ID"
   - "Reference #18."          # Akamai
   - "The requested URL was rejected"  # BIG-IP ASM
   - "Pardon Our Interruption"         # Distil/Imperva
   ```

2. **The escalation ladder has only two rungs, both from the same IP.** `_proxies()`
   returns `None` unless all four `PROXY_*` variables are set; there is no evidence
   in the run log of a proxy attempt, so the secrets are either unset or the proxy
   is blocked too. For a WAF that filters on IP reputation, a residential proxy is
   the only thing that works — or you change source. The DTA publishes the same
   policy content as downloadable documents; monitoring those is more stable than
   scraping a WAF-protected SPA anyway.

**`NSW Government AI Guidance` — the Assurance Framework URL is dead.**

```
https://www.digital.nsw.gov.au/policy/artificial-intelligence/nsw-artificial-intelligence-assurance-framework
→ HTTP 404
```

NSW restructured that section. The content now lives at:

```
https://www.digital.nsw.gov.au/policy/artificial-intelligence/ai-governance-assurance-and-frameworks/nsw-ai-assessment-framework
```

The dashboard reports the failure as **`block_page: matched failure signature "This
site can't be reached"`** — that is Chrome's network error page from the Selenium
fallback, and it points a reader at a connectivity problem when the actual problem
is a moved page. See §3.3.

**Also in that set, and unrelated to it:**

```
https://www.asbfeo.gov.au/disputes-assistance/dispute-support
```

That is the *federal* Small Business and Family Enterprise Ombudsman's dispute
referral tool. It is not NSW, and it is not AI policy. It also extracts 85 KB
against 12 KB for the genuine NSW page, so it dominates that set's diff surface —
any change to it will be reported to a steward as *"NSW Government AI Guidance has
changed"*. Remove it, or give it its own set under a category that makes sense.

**And the baselines are poisoned.** `hashes.json` currently stores
`length: 347 / 355 / 355 / 359` for the four digital.gov.au documents and
`length: 84` for the NSW one. Those are WAF pages and error pages recorded as
baselines before validation shipped, and nothing will ever clean them up —
`validate_capture` only updates `length` on a *passing* capture. Any repair needs to
delete those document records so the next run treats them as first captures.

### 3.3 — Link rot is misreported as an infrastructure failure (High, S)

A 404 or 410 means *"a human needs to update a URL"*. A block page means *"the
fetcher needs a different route"*. They are completely different tasks and the
system currently collapses them into one `suspect_scrape` bucket with whatever
error text happened to come back last.

This matters enormously once sources are managed through a GUI (§5) — link rot
becomes the dominant failure mode the moment non-engineers start adding pages.

**Fix.** Add a `DOC_GONE = "link_rot"` outcome. In `_http_fetch`, treat 404/410 as
terminal and distinct (don't render, don't retry, don't proxy). In `health.py`, give
it its own alert kind. In the UI: *"This page no longer exists at the URL we have.
The source needs a new URL."* with the URL shown and a link to the editor.

### 3.4 — Priority inflation makes the badge meaningless (High, M)

From `history.json`, criticals as a share of analyses per month:

```
2025-09 → 2026-02   0% critical   (91 analyses, none critical)
2026-03            21%
2026-05            83%   (10 of 12)
2026-06            65%   (28 of 43)
2026-08            43%
2026-09            33%
```

Something changed around March 2026 — model version, prompt, or both — and the
scale collapsed. Today, **three of eight sets wear a `critical` badge**. Nothing in
the system measures whether any of them predicted anything.

The prompt's priority definitions are reasonable in isolation but have no anchor:
"directly alters user rights, data handling, liability or legal obligations"
describes *most* terms-of-service edits. Fixes, cheapest first:

1. **Anchor with examples in the prompt.** Two or three worked examples per band,
   drawn from your own archive. Few-shot anchoring is the single most effective
   lever and costs ~300 prompt tokens.
2. **Make the model quote its evidence.** Add a required `evidence` key: the
   specific added or removed line the priority rests on, verbatim from the diff.
   Reject the response if the quoted string isn't present in the diff. This is a
   cheap hallucination check *and* it lets the UI show "critical — because of this
   line", which a reader can verify in seconds.
3. **Add a `confidence` field** and fade low-confidence badges the way stale ones
   already fade.
4. **Report calibration.** You already have 👍/👎 feedback opening GitHub issues;
   nothing aggregates it. A `feedback.json` and one line on the About modal —
   *"192 analyses, 48 rated critical, 6 confirmed useful by a steward"* — would tell
   you within a month whether the scale means anything.

### 3.5 — Transient API errors are misfiled as schema failures (High, S)

`steward/analysis.py:212` runs exactly two attempts with **no delay between them**,
and treats an API exception identically to a malformed response. Of the three
failed analyses in the run log:

```
2026-08-23  Google      missing required key(s): priority     ← genuine schema failure
2026-09-04  Google      503 UNAVAILABLE (high demand)         ← transient API error
2026-09-12  Anthropic   503 UNAVAILABLE (high demand)         ← transient API error
```

Both 503s hit the same demand spike twice in a row because there is no backoff.
Both then incremented `entry["schema_failures"]` (`main.py:530`), which at threshold
2 raises a health alert reading *"the model returned an invalid response on
consecutive runs"* — which is false, and sends you looking in the wrong place.

**Fix (three small changes):**
- Separate `AnalysisOutcome.error_kind` into `api_error` vs `schema_error`.
- Retry API errors 3× with exponential backoff and jitter (2s, 8s, 30s); keep
  schema retries at one corrective re-ask.
- Only count `schema_error` toward `schema_failures`; give `api_error` its own
  counter and a different alert.

The revert logic in `_revert_changed_documents` is genuinely well designed — the
diff isn't lost, it's retried next run — so the real cost of a 503 today is one day
of latency plus a misleading alert. Worth fixing anyway.

### 3.6 — Gemini structured output is being left on the table (Medium, S)

`steward/analysis.py:220` sets `response_mime_type="application/json"` but not
`response_schema`. The `google-genai` SDK supports a response schema with enum
constraints, which makes `missing required key(s): priority` and an out-of-enum
priority **structurally impossible** rather than caught after the fact:

```python
config=types.GenerateContentConfig(
    response_mime_type="application/json",
    response_schema={
        "type": "object",
        "required": ["verdict", "summary", "analysis", "priority", "evidence"],
        "properties": {
            "verdict":  {"type": "string", "enum": list(VERDICTS)},
            "priority": {"type": "string", "enum": list(PRIORITIES)},
            "summary":  {"type": "string"},
            "analysis": {"type": "string"},
            "evidence": {"type": "string"},
        },
    },
)
```

Keep `parse_and_validate` as belt and braces — it also does the
`no_material_change → priority=low` coercion, which the schema can't express — but
this removes a whole failure class for about fifteen lines.

### 3.7 — Nothing watches the watcher (Medium, S)

If the GitHub Actions workflow stops running — disabled, a billing change, a
broken step before `main.py` — `hashes.json` freezes and **the dashboard looks
completely normal**. Every badge, every "last checked", every health pill shows the
last known state as though it were current. That is the exact silent-false-negative
failure mode the health system was built to eliminate, one level up.

**Fix.** `health.json` already carries `generated_at`. Read it in `usePolicySets`
and render a page-level banner when it is more than 48 hours old:
*"The monitor last completed a run N days ago. Everything below may be out of
date."* Ten lines, and it closes the last hole in the trust chain.

### 3.8 — Snapshot writes and `hashes.json` are not atomic (Medium, M)

`process_policy_set` writes per-document snapshots during the loop
(`_commit_texts`), but `hashes.json` is written once at the very end
(`main.py:717`). If the run dies in between — and the workflow makes that more
likely than it sounds, see below — you get a snapshot on disk that is *newer* than
the hash recorded for it. On the next run:

1. The fetched text matches the stored snapshot, so the diff is empty.
2. Empty diff → the cosmetic gate → `DOC_UNCHANGED`.
3. The new hash is written.

**A real change is silently swallowed and never analysed.** Low probability, but
the failure is exactly the one the whole project exists to prevent, and it is
invisible when it happens.

Two contributing factors in `.github/workflows/update_checker.yml`:
- `concurrency: cancel-in-progress: true` (line 27) means any push to `main`
  touching `src/**` kills a scheduled run **mid-flight**.
- `continue-on-error: true` on the run step means a partial run still commits
  whatever is on disk.

**Fix.** Cheapest: set `cancel-in-progress: false` for the data job and write
`hashes.json` after each set rather than once at the end. Better: stage snapshots
to `snapshots/.staging/` and move them into place only after `hashes.json` is
written.

### 3.9 — The validator's failure mode is biased toward silence (Medium, M)

Three related edges, all pointing the same way:

- **`growth_ratio: 2.5` rejects a doubled document as suspect.** But a policy
  doubling in size *is* the news — a consolidation, a major rewrite, a new
  arbitration section. Today that gets recorded as a scrape failure and never
  reaches the model. Suggest: on `grew`, don't reject — analyse it, and tell the
  model *"this document more than doubled in length; that may be a capture error
  rather than an amendment — say which you think it is."* Let the model's
  `uncertain` verdict do the work it was designed for.
- **A first capture has almost no safety net.** `shrink_ratio` and `growth_ratio`
  only apply when `prior_length` exists (`validation.py:89`), so a brand-new
  source is checked against `min_length: 500` and the signature list alone. The
  522-character WAF page from §3.2 would pass. Suggest a **first-capture
  quarantine**: a new document's baseline isn't trusted until two consecutive runs
  agree on its hash, and the UI shows it as "establishing baseline". This becomes
  important the moment sources are added through a GUI.
- **`min_length` is global.** A one-paragraph AI principles page and the ACSC ISM
  have nothing in common. Make it overridable per URL in `policy_sets.json`.

### 3.10 — Health alerts fire every run, forever (Medium, S)

The workflow comments on the same open `source-health` issue on every run while a
source is failing. Digital.gov.au has been failing for 35 runs. That issue has
been commented on ~35 times with substantially the same table.

This is precisely why the two broken sources have sat for a month: the alert
carries no information because it's identical to yesterday's.

**Fix.** Alert on *state transitions only*: a source newly crossing into `failing`,
a source recovering, a new alert kind appearing. Keep a small `health_state.json`
of what was last alerted and diff against it. Then add a weekly digest comment for
anything still open. Recovery notifications are as valuable as failures — right
now nothing tells you a source came back.

## 5. The source-management GUI

### 5.1 — The governing decision: keep git as the source of truth

**Do not put `policy_sets.json` in a database.** The editor should read and write
the file in the repository through the GitHub API. Reasons, in order of weight:

1. **The whole system's integrity model is "the repo is the datastore."** A second
   source of truth will drift from the one `main.py` actually reads, and you will
   debug that drift at 11pm.
2. **Git already gives you the audit trail you would otherwise have to build.**
   Who added this source, when, why, and what did the list look like in March —
   `git log -p policy_sets.json` answers all four for free. For a government
   steward, that is not a consolation prize, it is a requirement.
3. **Rollback is `git revert`.** No migration, no undo table.
4. **It keeps the site a static deploy.** The editor can be down and the dashboard
   still works, because the dashboard has no dependency on it.

The service is therefore an *authenticated, validating editor for one JSON file* —
not an application with state.

### 5.2 — Architecture (recommended: Render)

```
Steward's browser
      │  GitHub OAuth (authorization code flow)
      ▼
Render web service  ──── imports steward/ from this same repo ────┐
  /auth/callback    │                                             │
  /api/sources      │  GET/PUT policy_sets.json                   │
  /api/preview      │  ← runs the real fetch+extract+validate     │
  /api/watchlist    │                                             │
      │             └─────────────────────────────────────────────┘
      │  GitHub Contents API: commit to a branch, open a PR
      ▼
  repository ──→ existing daily workflow ──→ GitHub Pages
```

**Why Render rather than a pure client-side editor:** a single-page app cannot hold
an OAuth client secret, so the alternative is asking the steward to paste a
personal access token into the browser — poor UX and a genuine security smell. You
already have the Render account; a ~250-line FastAPI service closes the gap and
unlocks the preview endpoint below, which is the feature that actually justifies
the GUI.

**Deploy the same repository to Render with a different start command.** The service
then does `from steward import fetching, validation, content` and uses the
*identical* code path the pipeline uses. No duplicated logic, no drift. Add
`render.yaml` and a `web/` package; `requirements.txt` already covers it.

### 5.3 — Authentication and authorisation

**Recommended: GitHub OAuth with a server-side allowlist.**

- The steward signs in with the GitHub account that already has access to the repo.
- The service holds `GITHUB_CLIENT_ID` / `GITHUB_CLIENT_SECRET` in Render's
  environment.
- `ALLOWED_LOGINS` env var: a comma-separated list of GitHub usernames. Checked
  **server-side on every write**, never in the client.
- Session: a signed, `HttpOnly`, `Secure`, `SameSite=Lax` cookie, 8-hour expiry.

Why this rather than a password or magic link: no user table, no password storage,
no reset flow, MFA inherited from GitHub, and the identity is *the same identity*
that appears in the commit history. It is less code and stronger.

**If your colleagues don't have GitHub accounts**, the fallback is email magic-link
auth using the same Gmail account you're setting up for newsletters, with an
allowlist of addresses and the same signed-cookie session. Rank it second; it's
more code and a weaker audit trail.

**Non-negotiables regardless of which you pick:**

| | |
|---|---|
| **Server-side authorisation** | The allowlist check happens on the endpoint, not in the UI. Hiding a button is not access control. |
| **One validator** | The write path must call the same `validate_policy_sets` as `main.py` — hence §3.11a. |
| **URL scheme check** | Reuse `fetching.is_safe_url`. `file://` and `javascript:` in a data file must never become a fetch. |
| **SSRF protection** | **This is the one genuinely new attack surface.** `/api/preview` fetches an arbitrary user-supplied URL from inside your Render network. Resolve the hostname and reject the *resolved IP* if it is loopback, private (10/8, 172.16/12, 192.168/16), link-local (169.254/16 — cloud metadata), or IPv6 equivalents. Re-check after redirects. Do not skip this. |
| **Rate limiting** | On `/api/preview` especially — it is an outbound-fetch primitive. |
| **CSRF** | `SameSite=Lax` plus a double-submit token on writes. |
| **Attribution** | Commit as a bot identity with `Co-authored-by:` or a trailer naming the acting GitHub user, so `git log` answers "who added this". Require a one-line reason on delete. |

### 5.4 — The feature that makes it worth building: "Test this source"

Everything above is plumbing. **The preview endpoint is the product.**

When a steward pastes a URL, before anything is saved, show:

```
https://www.digital.gov.au/policy/ai/implementation

  HTTP 200 · plain fetch · 0.8s
  Extractor: trafilatura          Extracted: 256 characters
  ✗ VALIDATION FAILED — too_short: 256 chars is below the 500 char minimum

  First 500 characters of what we extracted:
  ┌─────────────────────────────────────────────────────────────┐
  │ Here are some possible reasons why your information cannot   │
  │ be processed... A high volume of simultaneous submissions... │
  └─────────────────────────────────────────────────────────────┘

  ⚠ This looks like a bot-protection page, not policy content.
    Try: [ Render with a browser ]  [ Use a CSS selector… ]  [ Route via proxy ]
```

That panel, at add-time, is what would have stopped the digital.gov.au source ever
being added in its current form — and it's what stops the *next* one. It also
catches the ASBFEO mis-file, because showing 85 KB of "Dispute Support is an online
referral tool" next to a set called "NSW Government AI Guidance" makes the mistake
obvious.

Extend it with a **selector tuner**: type a CSS selector, see the character count
and extracted text update live. That turns the single most fiddly part of adding a
source into a two-minute job.

**One caveat, and it's a feature:** Render's IPs are datacenter IPs, so a
WAF-blocked site will fail the preview exactly as it fails in CI. You learn at
add-time that the source needs `render: true` or a proxy, rather than a month
later. Headless Chrome on Render's low tier needs a Docker image and memory
headroom — if that's tight, make browser rendering an optional preview mode and
degrade gracefully to *"plain fetch only — this source may need rendering."*

Render's free tier spins down after inactivity, so expect a ~50 second cold start.
For a tool used weekly that's fine; just say so in the UI (*"waking the editor…"*).

```jsonc
      "url": "https://...",
      "label": "AI Assessment Framework",
      "selector": "main",
      "render": false,
      "force_proxy": false,
      "min_length": 800         // NEW — per-URL override, see §3.9
    }
  ]
}
```

**`enabled: false` rather than deletion is important.** Removing a set outright
orphans its snapshots, diffs and a year of archived analyses — `UPGRADE_PLAN.md`
§E4 is a list of exactly those orphans from the last time it happened. Have
`main.py` skip disabled sets while keeping them in `hashes.json`, and grey them out
in the sidebar under "No longer monitored".

While you're there, let the editor manage `steward_config.yaml`'s
`fingerprint.watchlist` too. It is the other thing a steward will genuinely want to
change, and today it's a code change.

## 6. The news feed

`UPGRADE_PLAN.md` §C is a good plan — the `List-Id` insight, the four-band APS
relevance rubric, storing TLDRs rather than bodies, and the cross-link to monitored
policies are all right. Three changes I'd make.

### 6.1 — Do RSS first, email second

This is the main recommendation in this section. **Most of what you want is
available as a feed, and RSS needs no mailbox, no credential, no app password, no
deduplication puzzle, and no LLM call to split an issue into stories.** An Atom
entry *is* a story.

You could have a working news tab in three or four days from:

- `.gov.au` newsrooms and media-release pages — most Drupal/GovCMS sites expose
  `/rss.xml` or `?_format=rss`
- OAIC, ACSC/ASD advisories, the DTA, APSC
- InnovationAus, The Mandarin, iappANZ
- arXiv `cs.CY` / `cs.AI` with a keyword filter, if you want research
- Vendor changelogs and blogs: Anthropic, OpenAI, Google AI — **these are the
  highest-value feeds you have**, because they announce the policy changes your
  pipeline then detects

Email ingestion is only needed for newsletters with no feed (Import AI, Transformer,
Platformer, Ben's Bites, TLDR AI). Build it once RSS has proved the UI and the
relevance rubric, so you're debugging one hard thing at a time.

Implementation is small and fits the existing shape exactly:

```
feeds.yaml                 # url, display name, publisher, default relevance floor
steward/feeds.py           # fetch + parse (feedparser), dedupe on entry id/link
steward/news.py            # one LLM call per batch → TLDR + topics + aps_relevance
news/feed.json             # rolling 30 days — what the app fetches
news/archive/YYYY-MM.json  # everything older
```

Add `feedparser` to `requirements.txt` and a second job (or a second cron) to the
workflow. Same flat-file discipline, same static deploy.

### 6.2 — Gmail specifics, when you get there

- Dedicated Google account, not yours. Enable 2FA, then generate an **App Password**
  (plain IMAP passwords haven't worked since 2022). `imap.gmail.com:993`.
- **Do not use `UNSEEN` as the queue.** Anything that touches the mailbox — you, on
  your phone, once — flips the flag and the item is silently lost forever. Keep
  `news/processed_ids.json` of `Message-ID`s as the authority and treat read state
  as a convenience only. `UPGRADE_PLAN.md` C1 gets this half right; make the ID
  file the source of truth.
- Turn off Gmail's category tabs and smart features on that account, or everything
  lands in Promotions and `INBOX` searches miss it.
- Match newsletters on `List-Id`, not `From` — senders rotate ESP subdomains
  constantly. This is the best single idea in the existing plan. Unmatched senders
  go to a quarantine bucket you promote or block from the UI; a public signup
  address collects spam within weeks.
- Keep the address off the repo and off the site.

### 6.3 — Three additions to the existing plan

1. **Verify every URL the model returns.** Newsletter and feed text is untrusted
   input flowing into a prompt whose output is rendered as markdown. §C7 covers
   fencing and `http(s)` validation. Add: **check that each returned `source_url`
   actually appears in the source document.** A model that invents a link is worse
   than one that omits it, and this is a five-line check.
2. **Promote the cross-link (C5) to a first-class feature.** *"Anthropic's terms
   changed on 13 September — here are the four news items about it"* is the thing
   that makes this a steward's tool rather than another aggregator. It's a
   dictionary lookup on vendor names and domains. No vectors, no graph.
3. **Send the digest back out.** You have a Gmail account and a
   `buildBriefing()` function that already produces the markdown. A weekly
   "AI policy watch" email to an allowlist of colleagues, combining policy changes
   and news at relevance ≥ 2, is maybe half a day on top of what you'll already
   have built — and it is how this tool actually reaches people who won't visit a
   dashboard.

**Cost check:** ~20 items a day at ~4k tokens on Gemini Flash is single-digit
dollars a year. Not a constraint.

**Copyright:** store the link, your own TLDR, and metadata — never the body. Strip
UTM parameters at ingest and never render remote images; newsletter HTML is full of
tracking pixels. Both are cheap now and awkward to retrofit.

## 7. UX suggestions not already covered

1. **A "what changed since I last looked" marker.** Store the last-visit timestamp
   in `localStorage` and mark rows new since then. The dashboard's 7-day window is
   arbitrary; "since you last looked" is what the question actually is.
2. **Show the evidence line on the card.** Once §3.4's `evidence` field exists,
   putting the quoted clause directly on the briefing row means a steward can
   triage without opening anything.
3. **"Not monitored" should be visible.** A steward's second question after "what
   changed" is "are we watching X?". A searchable list of monitored sources with
   an "add this" button — going straight to the §5 editor — closes that loop.
4. **Per-document badges.** See §3.11e. "Anthropic — *Acceptable Use Policy*
   changed" is far more useful than "Anthropic Legal Policies changed".
5. **The health pill needs a third state.** `ok` / `degraded` / `failing` doesn't
   distinguish *"we can't read this"* from *"this page is gone"* (§3.3) or
   *"establishing baseline"* (§3.9). Those need different words because they need
   different actions.
6. **Mobile.** There are four media queries now, up from one — better than the plan
   claimed. The sidebar-plus-content layout still deserves a real pass; this is a
   thing people check on a phone on the train.

## 8. On the "AI Steward Implant" (RAG)

Your instinct in `THINGS I WANT TO IMPROVE.md` — that this is a time and money sink
— is correct about the version you described. It is not correct about the version
you actually need.

**You do not need vectors.** Your entire corpus is 192 archived analyses (956 KB of
JSON), 8 current analyses, a year of diffs, and — once §6 ships — a few thousand
news TLDRs. That is small. Embeddings and a vector store start earning their keep
somewhere north of ~10,000 documents; at roughly ten policy changes a month you are
years from that, and you'd be paying storage and complexity the whole way.

**The cheap 80%, in rough order of effort:**

1. **Client-side full-text search (1–2 days).** Generate a `search_index.json` at
   the end of each run — summaries, analyses, changed document labels, watchlist
   tags, news TLDRs. Ship MiniSearch or Lunr in the SPA. Instant, free, offline,
   no backend. This alone answers most of "what did we say about arbitration?".
2. **`/ask` on the Render service (2–3 days), once it exists for §5.** Keyword
   retrieval over the same index → top 10 chunks → one Gemini call with a
   **citations-required** prompt: every claim must name the analysis it came from,
   and the UI links to it. Retrieval-augmented, no vectors.
3. **SQLite FTS5 if keyword search runs out (1 day).** BM25 ranking, one file, no
   service. Still not a vector database.

Only consider embeddings if (2) demonstrably fails on real questions — and if it
does, you'll know exactly which questions, which is a much better place to start
than "implement RAG".

The RAG theory practice you're after is mostly in the retrieval and evaluation, not
the vectors. Building (2) with a citation requirement and a small eval set of
twenty real questions will teach you more than a vector pipeline that returns
plausible nonsense.

## 10. One closing observation

The most striking thing in this repository is the distance between the quality of
the *reasoning* and the state of the *running system*. `BACKEND.md` explains why
each gate exists, with the incident that motivated it. The tests pin those
incidents as fixtures. The comments explain intent rather than mechanics. That is
better than most professional codebases.

And the live site shows a critical badge dated 16 May 2024, on an analysis of a
Chrome error page, for a source that has been read successfully every day since.

The fix is not more engineering. It is a small amount of operational discipline
attached to the machinery that already exists: alert on changes rather than states,
make failures actionable rather than merely visible, and treat a source that has
never been read as a bug rather than a row in a table. Everything in §3.1 through
§3.3 is under a day's work, and it is worth more than either feature you asked
about.
